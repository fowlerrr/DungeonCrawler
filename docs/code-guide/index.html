Part I · Chapter 1 of 13

Welcome: One Brain, Two Skins

Dungeon Crawler is one game you can play two totally different ways — as a flat, top-down 2D dungeon crawl, or as a first-person 3D one. Here's the trick: it's not two games. It's one set of rules wearing two different costumes.

Open up the project's src/ folder and you'll find three main directories:

  • src/game/ — the rules. Maze generation, combat math, items, saving. Plain TypeScript. No drawing, no graphics library, nothing that knows what a pixel or a polygon is.
  • src/phaser/ — the 2D skin. Uses a library called Phaser to turn those rules into sprites you see from above.
  • src/three/ — the 3D skin. Uses a library called Three.js to turn the exact same rules into a first-person 3D world.

Why split it up like this? Because a monster's health, a maze's layout, and how much damage a sword does shouldn't care whether you're looking at them from above or walking through them in first person. Those are facts about the game, not facts about how it looks. Keeping them separate means a bug fix or new feature in the rules automatically works in both views — you'll actually see this happen in a later chapter, where one bug fix in src/game/ fixed the exact same problem in both the 2D and 3D clients at once.

How to read this guide

Each chapter builds on the last, starting with the simplest, most self-contained ideas (how a maze gets built) and working up to the ideas that tie everything together (how the whole app boots up and switches between 2D and 3D). You can jump around using the map on the left, but it's built to be read in order the first time through.

Every code snippet you'll see is copied straight from this project's real source files — you can open them yourself in src/ and find the exact lines. Boxes titled What's happening translate the code into plain English. Boxes titled Go deeper are optional — expand them if you're curious, skip them if you're not.

Building the Dungeon
Part I · Chapter 2 of 13

Building the Dungeon

Every time you start a new level, the game builds a brand-new maze from scratch — corridors, locked vaults, keys, all of it. It does this with a short pipeline of small, focused steps, each living in its own file under src/game/maze/.

Step 0: a dice that always rolls the same way

Mazes need randomness, but Math.random() can't be controlled — you can't ask it to reproduce the exact same "random" maze twice. So the project has its own tiny random number generator, Rng, that starts from a seed number:

export class Rng {
  constructor(seed: number) { ... }
  next(): number       // a float between 0 and 1
  nextInt(max: number): number
  pick<T>(items: readonly T[]): T
}

src/game/maze/rng.ts

What's happening
  • Give it the same seed number twice, and next() produces the exact same sequence of "random" numbers both times.
  • That means generateLevel(42, ...) always builds the identical maze — handy for testing, and it's the reason the whole generation pipeline below can be trusted to behave predictably.

Step 1: carve a perfect maze

The first real step is generateBaseMaze(). Picture standing in a grid of rooms with every wall still up. You dig into a random neighboring room, mark it visited, and repeat — always digging into unvisited rooms only. When you get stuck (every neighbor already visited), you backtrack to the last room that still has an unvisited neighbor and keep digging from there.

while (stack.length > 0) {
  const current = stack[stack.length - 1];
  const candidates = adjacency.get(current).filter(e => !visited.has(e.other));
  if (candidates.length === 0) { stack.pop(); continue; }   // dead end — backtrack
  const chosen = rng.pick(candidates);
  chosen.edge.open = true;                                   // knock the wall down
  visited.add(chosen.other);
  stack.push(chosen.other);
}

src/game/maze/generator.ts — simplified

What's happening
  • This is a classic algorithm called a randomized depth-first search (or "recursive backtracker") — dig forward randomly, back up when stuck.
  • The stack array is standing in for backtracking — normally you'd write this with a function that calls itself, but a big maze could call itself so many times the program would crash. Using an array as an explicit stack does the same job without that risk.
  • The result is a perfect maze: every room is reachable, and there's exactly one path between any two rooms — no loops yet.

Step 2: knock down a few extra walls

A perfect maze with zero loops feels like a single long, winding hallway — not much fun to explore. So braidMaze() goes back over every wall that's still standing and, for each one, has a chance (braidFactor, like 0.3 for 30%) of knocking it down too:

for (const edge of graph.edges) {
  if (!edge.open && rng.next() < braidFactor) {
    edge.open = true;
  }
}

src/game/maze/braiding.ts

This is always safe to do — every wall still standing already has some other path around it (that's what "every room is reachable" from Step 1 guarantees), so opening more walls can only add shortcuts and loops, never break anything.

Step 3: lock a few dead ends behind doors

Now for the vaults. The game needs to pick a few walls to turn into locked doors, each one sealing off a small dead-end area (a "vault") that you can only reach once you've found the matching key elsewhere in the maze.

The tricky part: lock the wrong wall, and you could accidentally seal the exit — or seal away a key needed to open some other door — making the level impossible to finish. placeLocks() avoids this with a clever trick from graph theory:

What's happening
  • A bridge is an edge that is the only path between two parts of the maze — remove it, and those parts become totally disconnected from each other.
  • findBridges() finds every bridge in the maze using a well-known algorithm (Tarjan's bridge-finding algorithm). Only bridges are ever candidates for a locked door — locking a non-bridge wall wouldn't actually block anything, since there'd always be another way around.
  • For each candidate bridge, the game checks: how many rooms would this seal off? If it's a small, self-contained pocket (4 rooms or fewer) that doesn't contain the exit or another door's key, it becomes a real locked door — and the key gets dropped somewhere else in the maze.
Go deeper: how does the game find a "bridge"?

It's a walk through the maze (a depth-first search) that tracks two numbers per room: the order it was discovered in, and the lowest discovery number reachable from it by any route that doesn't just backtrack the way it came. If a neighboring room can't "reach back" to anything before the current room through some other path, the wall between them must be the only connection — a bridge. It's implemented with an explicit stack (same reason as Step 1) so it doesn't blow up on a big maze.

Step 4: double-check it's actually solvable

Even with all that care, validateSolvable() runs one more independent check before the level is accepted — it walks the maze from the entrance, remembering not just which room it's in but which keys it's picked up along the way, and confirms there's some route to the exit. If that check ever fails, level.ts just throws the whole maze away and generates a new one with a different seed, up to 10 times, before falling back to a maze with no locks at all (which is always solvable, since it's just the base maze from Step 1 and 2).

Step 5: turn it into an actual grid

Everything so far has been abstract — "rooms" and "walls between them," not pixels. The last step, rasterizeMaze(), converts that into a real 2D grid of tiles using a neat trick: a maze of N rooms across becomes a tile grid of 2N+1 tiles across. Every room becomes a floor tile at an odd position; every open wall between two rooms becomes a floor tile squeezed in between them; everything else stays a wall.

Try it yourself
In src/game/systems/LevelConfig.ts, the maze's braidFactor grows slightly with level number. Try hard-coding it to 0.05 (almost no loops — a maze-y maze) or 0.8 (loops everywhere — an open room) and see how differently the same generator feels to walk through.

Talking in Coordinates
Part I · Chapter 3 of 13

Talking in Coordinates

The last chapter ended with rooms turning into tiles. This short chapter covers a detail that trips people up constantly once rendering gets involved: the game actually uses three different coordinate systems, depending on what it's talking about.

  • Cell space — a room in the maze, like {x: 2, y: 1}. This is what the generator from Chapter 2 works in.
  • Tile space — a square in the rendered grid, like {tx: 5, ty: 3}. Remember the "2N+1" trick — tile coordinates aren't the same numbers as cell coordinates.
  • Pixel space — an actual on-screen position, like {x: 176, y: 112}, found by multiplying a tile coordinate by TILE_SIZE (32 pixels).

All these conversions live in one file, so nobody has to redo the math by hand:

export function cellToTile(c: Cell): { tx: number; ty: number }
export function tileCenterPx(tx: number, ty: number): { x: number; y: number }
export function cellCenterPx(c: Cell): { x: number; y: number }
export function pxToTile(x: number, y: number): { tx: number; ty: number }

src/game/maze/raster.ts

Can I see that? (Line of sight)

Coordinates matter most when the game needs to answer a question like: "can this arrow actually reach that goblin, or is there a wall in the way?" hasLineOfSight() answers this by sampling points along the straight line between two pixel positions — every quarter-tile — and checking each one lands on a floor tile, not a wall:

for (let i = 1; i < steps; i++) {
  const t = i / steps;
  const x = fromX + (toX - fromX) * t;
  const y = fromY + (toY - fromY) * t;
  const { tx, ty } = pxToTile(x, y);
  if (grid[ty][tx] !== TileType.Floor) return false;   // hit a wall along the way
}
return true;

src/game/maze/lineOfSight.ts — simplified

A close cousin, raycastDistance(), does almost the same walk but in a direction instead of toward a fixed point — it's what makes a missed arrow stop exactly at the wall it would hit, instead of sailing straight through it. (This was an actual bug fixed during development — you'll hear more about it in Chapter 5.)

Player, Monsters, and .logic

Time to meet the actual characters. And right away you'll run into the single most important design pattern in this whole codebase — one you'll see reused, unchanged, all the way through both the 2D and 3D skins.

Surprisingly small classes

Here's the entire Player class:

export class Player {
  hp: number;
  maxHp: number;
  x = 0;
  y = 0;
  lastAttackAt = -Infinity;
  lastHitAt = -Infinity;

  constructor(maxHp: number) {
    this.maxHp = maxHp;
    this.hp = maxHp;
  }
}

src/game/entities/Player.ts

No facing direction, no drawing code, no sprite, no controls. Just health and position. The Monster class is just as bare — health, damage, position, and a computed isDead flag:

export class Monster {
  readonly defId: string;
  hp: number;
  maxHp: number;
  damage: number;
  x = 0;
  y = 0;

  get isDead(): boolean { return this.hp <= 0; }
}

src/game/entities/Monster.ts — trimmed

The pattern: one brain, worn by two bodies

So where does the player's on-screen body actually live? In the 2D skin, a class called PlayerSprite owns the real Phaser sprite and physics body — and holds a reference to a plain Player as this.logic. Every time the sprite moves, it copies its new position back into logic.x/logic.y. In the 3D skin, PlayerController3D does the exact same job for a Three.js camera and mesh instead.

Why bother?
  • Anything that needs to know "is the player near this monster?" or "what's the player's HP?" can ask the plain Player object, without needing to know or care whether Phaser or Three.js is currently running.
  • This is exactly how Combat.ts (next chapter) works against both skins with zero duplicated code.

Same template, different toughness

Monsters are built from a shared template (a MonsterDef — "a goblin has 12 HP and deals 3 damage") plus two multipliers supplied by the current level's difficulty settings:

constructor(def: MonsterDef, hpMult = 1, damageMult = 1) {
  this.defId = def.id;
  this.maxHp = Math.round(def.baseHp * hpMult);
  this.hp = this.maxHp;
  this.damage = Math.round(def.baseDamage * damageMult);
}

src/game/entities/Monster.ts

So the goblin template you fight on level 1 is the exact same data as the goblin template on level 20 — it's just multiplied up to be much tougher by then. The full roster spans six tiers (Slime and Goblin at tier 1, all the way to a Succubus and a Magma Golem at tier 6), unlocking gradually — and once a tier unlocks, it never goes away, so a deep level can still throw an easy Slime at you alongside something much scarier.

Fighting: The Combat System
Part II · Chapter 5 of 13

Fighting: The Combat System

Every attack in this game — swinging a sword, firing an arrow, a goblin clawing at you — runs through the same small set of pure functions in one file: Combat.ts.

No dice rolls

Something worth knowing up front: there's no random "miss chance" anywhere in this combat system. If a target is in range and in front of you, the attack lands — always. Combat here is about positioning (are you close enough, facing the right way?), not luck.

Cooldowns are just timestamps

export function canAttack(player: Player, now: number, cooldownMs: number): boolean {
  return now - player.lastAttackAt >= cooldownMs;
}

src/game/entities/Combat.ts — simplified

No timers, no counters ticking down — just "has enough time passed since the last attack?" The same trick (canBeHit) gives the player a brief invincibility window after being hit, so standing next to a monster doesn't melt your health bar instantly.

Melee hits everyone in the cone. Ranged hits the nearest.

A melee swing checks every monster within range and within an angle in front of you (the "attack cone") — and hits all of them at once. A ranged shot instead picks only the single nearest target, like an arrow that stops at the first thing it hits:

export function selectAttackTargets<T>(origin, facing, range, coneHalfAngleDeg, candidates: readonly T[]): T[]
export function selectNearestTarget<T>(origin, candidates: readonly T[]): T | undefined

src/game/entities/Combat.ts

Defense subtracts, it doesn't multiply

export function mitigateDamage(amount: number, defense: number): number {
  return Math.max(1, amount - defense);
}

src/game/entities/Combat.ts

Simple subtraction, floored at 1 — no amount of armor makes you completely untouchable. Note this only ever applies to damage you take; monsters have no defense stat of their own, so your attacks always deal their full damage.

Weapon "art" is just a costume

Weapons have an art field — "sword", "axe", "fireball", and so on — but it has zero effect on the math above. It only picks which swipe or projectile image gets drawn. A dagger with art: "sword" would fight identically to one with art: "dagger" — only the animation would look different.

A real bug, fixed while building this game
A missed ranged shot used to fly straight through walls, because its "miss" destination was computed with pure geometry (start point + direction × range) with no idea a wall might be in the way — unlike a hit, which is always a real monster's position, already guaranteed to be somewhere reachable. The fix was raycastDistance() from Chapter 3: instead of always traveling the weapon's full range, a miss now stops exactly at the nearest wall along its path. Because both the 2D and 3D skins call the same Combat.ts/lineOfSight.ts functions, one fix in src/game/ repaired the bug in both skins at once.

Loot and Gear

Every weapon, piece of armor, and accessory in the game is just an entry in a plain array — no magic, no procedural stat rolling. Here's the whole shape:

export interface ItemDef {
  id: string;
  name: string;

  rarity: "normal" | "rare" | "epic" | "legendary";
  stats: ItemStats;

  description: string;

src/game/data/weapons.ts — trimmed

Notice the bow deals slightly less damage but has almost 3× the range and no ranged: true flag missing — that flag is literally what tells combat code to use selectNearestTarget instead of the melee cone from the last chapter.

Rarity: a ladder, not a coin flip

There are four rarity tiers, each with a color and a base "drop weight" — how likely a chest is to roll that tier:

Normal
weight 100
Rare
weight 5
Epic
weight 1
Legendary
weight 0.15

Those weights aren't percentages by themselves — a chest adds up all the weights of everything it could possibly drop and picks proportionally, the way a raffle with more tickets in the jar is more likely to be drawn. Deeper levels shift the odds toward the rarer tiers, so legendary gear stays a real event even late in a run, not a guarantee.

Deciding what to auto-equip

When "auto-equip better gear" is turned on, the game needs to answer: is this new item actually an upgrade? For weapons, it compares damage per cooldown millisecond — a rough damage-per-second rate, so a slow hard-hitting mace can fairly be compared against a fast light dagger. For armor, it's just raw defense. Accessories are skipped entirely — their stats (like a speed boost) don't reduce to one comparable number cleanly enough to auto-decide for you.

Growing Stronger, Saving Up
Part II · Chapter 7 of 13

Growing Stronger, Saving Up

This game skips the usual "gain XP, level up" loop. Instead, progress is tied directly to how deep you've gone, and saved progress is deliberately narrow — just enough to feel earned, without needing to remember everything.

One stat point per level cleared

Clearing a dungeon level grants exactly one stat point, which you spend into attack, defense, or HP. The trade-off is intentionally uneven:

StatPoints →Why
Attack+1 damageA single point already swings a full hit either way.
Defense+1 defenseSame logic — subtracted straight off incoming damage.
HP+5 max HPOne extra HP alone is comparatively trivial, so it's worth more per point.

src/game/systems/PlayerProgression.ts

Difficulty is one formula, not a big lookup table

There's no hand-authored table of "here's what level 17 looks like." Instead, every difficulty knob is a small formula based on the level number, computed fresh each time:

mazeCols: clamp(10 + n, 10, 30),
monsterHpMult: 1 + (n - 1) * 0.15,
monsterDamageMult: 1 + (n - 1) * 0.06,
bossHpMult: 1 + (n - 1) * 0.3,

src/game/systems/LevelConfig.ts — trimmed

As n (the level number) climbs, the maze grows, monsters get tougher a bit faster than their damage grows, and the boss scales up even faster than regular monsters do — deliberately, so a boss fight still feels like a real event even after dozens of regular kills.

Saving: ids, not objects

What actually gets written to your browser's storage is surprisingly small — not full item data, just ids:

export interface PlayerProfile {
  equippedIds: Partial<Record<"weapon"|"armor"|"accessory", string>>;
  ownedIds: string[];
  levelNumber: number;
  highestLevelReached: number;
  gold: number;
  statAllocation?: StatAllocation;
}

src/game/systems/SaveManager.ts

Why ids instead of full items?
  • Loading a save looks up each saved id against the current item catalog (weapons.ts/items.ts) and pulls in whatever stats that item has right now.
  • That means if a weapon's damage ever gets rebalanced later, old saves don't break or go stale — they just quietly pick up the new numbers.
  • Unknown ids (from an item that's since been removed) are silently skipped rather than crashing the load.

Notably absent from the save: your current HP, the maze layout you're standing in, monster positions, and which keys you're currently holding. Only long-term progress survives between sessions — the exact stuff you'd actually feel bad about losing.

The Game Loop and Input
Part III · Chapter 8 of 13

The Game Loop and Input

Everything so far has been about what the game knows. Starting here, Part III is about how that knowledge actually ends up moving on your screen — beginning with the heartbeat that runs the whole show.

The loop

Both the 2D and 3D clients run the same basic cycle, roughly 60 times every second: read whatever input happened, update the game state based on it, then draw the current frame. Then do it again.

You saw the "update" step's shape already back in Chapter 4 and 5 — checking cooldowns, calling Combat.ts functions, moving the player. The "draw" step is the entire subject of the next two chapters.

One input model, two sources

Here's a neat trick worth calling out: the game code that reads "which direction is being held right now?" has no idea whether that came from a keyboard or a finger on a touchscreen. Both feed into the exact same tiny piece of shared state:

getDiscreteDirection(): Direction | null {
  return resolveDirection(this.heldOrder, (dir) =>
    this.virtualDown[dir] || this.keys[dir].some((k) => k.isDown)
  );
}

src/phaser/input/InputController.ts — simplified

The on-screen d-pad's buttons literally call pressVirtualDirection()/releaseVirtualDirection() — the exact same methods a keyboard event handler calls internally. From GameScene's point of view, there's no difference at all between a key press and a tap.

Drawing the World in 2D
Part III · Chapter 9 of 13

Drawing the World in 2D

The 2D client is built with a library called Phaser, organized as ten separate scenes — think of each one as its own mini-program that can be started, stopped, or run alongside others.

The scene map

Phaser gives you two different ways to switch scenes, and this game uses both on purpose: scene.start() stops the current scene and replaces it — a clean break. scene.launch() starts a new scene without stopping the current one, so both run at once — used for overlays like the pause menu, or the HUD sitting on top of gameplay.

This is also why GameScene and UIScene (the sidebar HUD) are two separate scenes rather than one: pausing gameplay (say, to open the inventory) must never pause the HUD along with it, or the sidebar would freeze mid-update. Keeping them separate means UIScene keeps rendering no matter what state GameScene is in.

GameScene: where the rules meet the picture

This is the scene where everything from Part II gets turned into visuals. Its update() method, called every frame, is short and readable once you know the pieces:

update(_time: number, delta: number): void {
  if (this.playerSprite.logic.hp <= 0) {
    this.scene.pause();
    this.scene.launch(SCENE_KEYS.GAME_OVER, { levelNumber: this.levelNumber });
    return;
  }
  const direction = this.inputController.getDiscreteDirection();
  if (direction) this.playerSprite.tryStep(...);

  for (const monster of this.monsterSprites) monster.step(this.playerSprite.x, this.playerSprite.y, delta);

  if (this.inputController.isAttackDown()) this.tryPlayerAttack();
}

src/phaser/scenes/GameScene.ts — trimmed

Notice this.playerSprite.logic.hp — that's Chapter 4's pattern in action. GameScene mostly reads/writes plain .logic fields and calls src/game/ functions; Phaser itself only handles the actual drawing, physics, and tweened movement.

Turning tiles into pixels

MazeRenderer.ts loops over the tile grid from Chapter 2 and places one image per tile — walls get a physics body for free collision, floor tiles get one of six pre-drawn "edge" images (rotated as needed) depending on which neighboring tiles are walls, so a floor tile next to a wall gets a matching decorative border. This trick — reusing a handful of images at different rotations instead of drawing every possible wall combination by hand — is called autotiling, and the logic for picking which variant to use lives back in src/game/maze/autotile.ts, not in the renderer itself.

Drawing the World in 3D
Part III · Chapter 10 of 13

Drawing the World in 3D

The 3D client, built with Three.js, is a single big class called Game3D — its own comment literally describes it as "everything GameScene, UIScene, and PauseScene do together, in one class." Same rules from Part II, first-person view.

The camera is the player

There's no player model to see, because there's nothing standing between you and the camera — the camera sits exactly where the player is standing, at a fixed eye height, and looks toward whatever direction the player is facing:

const world = pxToWorld(this.player.x, this.player.y);
const look = this.player.visualFacing;
this.camera.position.set(world.x, EYE_HEIGHT, world.z);
this.camera.lookAt(world.x + look.x, EYE_HEIGHT, world.z + look.y);

src/three/Game3D.ts — EYE_HEIGHT = 1.0

Turning doesn't snap instantly, either — the camera eases toward the new facing over 150 milliseconds using a separate visualFacing value, so a 90° turn feels smooth. The actual gameplay logic (which way an attack fires) still uses the instant, un-eased facing, so combat never feels laggy even while the camera is still catching up visually.

Revealing the maze tile by tile

Building 500 separate wall objects would be slow. Instead, MazeMesh.ts uses a Three.js trick called instancing: one wall shape, drawn hundreds of times in a single command, each copy just given a different position. Every tile starts scaled down to nothing (invisible), and gets moved into its real position only once fog-of-war has actually revealed it — and once revealed, a tile stays revealed. (A top-down 2D fog can fade a tile back to black once you walk away, but doing that in first person would look like a hallway ending in a solid wall of black a few steps ahead — so the 3D client deliberately never re-hides anything.)

Monsters that always face you

A 3D monster's body is actually flat — a single rectangle with a monster picture stamped on it, called a billboard. From the front it looks fully 3D; from the side, it would look like a paper cutout. So every single frame, the game manually rotates each monster to keep facing the camera, no matter where the camera moves:

faceCamera(cameraPos: THREE.Vector3): void {
  this.bodyMesh.lookAt(cameraPos.x, this.bodyMesh.getWorldPosition(new THREE.Vector3()).y, cameraPos.z);
}

Menus and Touch Controls

You've now seen both skins individually. This chapter covers how you actually pick one — and how the game adapts itself for players on a phone.

2D and 3D share one menu design

Both the 2D menu (MenuScene.ts, built with Phaser text objects) and the 3D menu (MenuScreen3D.ts, built with plain HTML/CSS) show the exact same idea: a small "2D / 3D" label pair, where whichever mode you're currently in is shown bold and highlighted, and the other one is a clickable link to switch:

label3D.setInteractive({ useHandCursor: true });
label3D.on("pointerdown", () => this.playIn3D());

src/phaser/scenes/MenuScene.ts

An important, easy-to-miss detail: quitting an in-progress 3D game back to the menu returns you to the 3D menu, not the 2D one — staying in the mode you were already in. Only clicking that menu's own "2D" label actually tears 3D down and rebuilds the 2D client. It's a small distinction, but it's the difference between a menu that respects which mode you're in and one that quietly resets you every time.

Designing for a thumb, not a mouse

One constant, computed once when the page loads, quietly reshapes a huge amount of the UI:

export const IS_TOUCH_DEVICE =
  typeof window !== "undefined" &&
  (window.matchMedia("(pointer: coarse)").matches || navigator.maxTouchPoints > 0);

src/config/device.ts

On a touch device, the 2D client actually renders at a smaller design resolution (480×380 for the maze view, versus 800×600 on desktop) rather than just scaling the desktop layout down — a scaled-down desktop layout would leave text and HUD elements too tiny to read. Both TouchControls.ts (2D) and TouchControls3D.ts (3D) only get constructed at all when IS_TOUCH_DEVICE is true, and they render as plain floating HTML buttons on top of the game canvas — not part of Phaser or Three.js at all — specifically so they survive scene changes and level rebuilds without needing to be recreated.

How It All Connects

Here's the entire boot sequence, start to finish — every piece you've met in this guide, in the order it actually happens the moment the page loads.

  1. index.html loads one script tag, pointing at src/main.ts.
  2. main.ts — three lines long — imports and calls bootPhaser(). That's its entire job.
  3. bootPhaser() constructs a Phaser.Game, registering all ten scenes from Chapter 9 up front, and only BootScene auto-starts.
  4. BootScene → PreloadScene → MenuScene — the placeholder-and-real-art textures load, then you land on the title screen from Chapter 11.
  5. From here, two paths:
    • New Game / Continue → scene.start(GAME, {'{'} fresh {'}'}) → GameScene calls generateLevel() (Chapter 2) and you're playing in 2D.
    • Clicking "3D" → MenuScene.playIn3D() calls destroyPhaser(), then dynamically loads and calls launch3D(), which shows MenuScreen3D — and picking New Game/Continue there constructs a Game3D, running the identical generateLevel() call.

Two small debugging conveniences worth knowing about, both dev-only: bootPhaser() stashes its game instance on window.game, and launch3D() stashes its on window.game3D — so while developing, you can open the browser console and poke directly at the running game state, in either mode.

The one rule that makes all of this possible
  • src/game/ never imports anything from src/phaser/ or src/three/ — the dependency only ever flows one direction.
  • Both skins are free to be built, torn down, and rebuilt independently, because neither one owns any rule the other depends on. That's the "one brain, two skins" idea from Chapter 1, now with every piece in between filled in.

Your Turn

Reading about code only gets you so far. The fastest way to actually understand any of this is to change a number, save the file, and see what happens. Here are some real, small, safe places to start — all constants you now know the meaning of.

  • Maze feel — braidFactor in src/game/systems/LevelConfig.ts (Chapter 2). Try 0.05 versus 0.8.
  • Vault size — MAX_VAULT_SIZE in src/game/maze/locks.ts (Chapter 2). What happens to the maze if locked vaults are allowed to be huge instead of tiny?
  • A new weapon — add an entry to the array in src/game/data/weapons.ts (Chapter 6). Give it a silly name, tune its damage/cooldownMs/range, and see it show up in your inventory.
  • Monster unlock pace — the minLevel values in src/game/data/monsters.ts (Chapter 4). Make the scary tier-6 monsters unlock at level 3 instead of 25, and see how fast that gets uncomfortable.
  • Stat point value — HP_PER_POINT in src/game/systems/PlayerProgression.ts (Chapter 7).
  • Attack cooldown — PLAYER_ATTACK_COOLDOWN_MS in src/config/constants.ts (Chapter 5).
  • The melee swipe's size — SWIPE_DURATION_MS and the ConeGeometry numbers in src/three/combat/AttackVisuals3D.ts (Chapter 10). This one isn't hypothetical — it's the exact spot that got tuned twice in a row during this project, first made much bigger because the original was too hard to see, then dialed back down because the bigger version overshot. Reading two real commits back to back (in the project's git history) that tweak the same three numbers is a genuinely good way to see how "tuning a game" actually feels in practice.
Where to look next
The test/ folder has a real Vitest test file for almost everything in src/game/ — reading test/lineOfSight.test.ts or test/level.test.ts is a great way to see, very concretely, exactly what a function is supposed to do in tricky edge cases (what happens when a wall sits right next to you?). The project's own README.md covers how to actually run the game and its tests locally.

That's the whole map. Every system in this game — the maze, the fights, the loot, both ways of drawing it, and the menu that lets you pick — is built from small, plainly-named pieces that each do one job and hand off cleanly to the next. That's not an accident; it's the single idea worth carrying forward into your own projects: keep the parts that decide things separate from the parts that draw things, and both get much easier to reason about.
